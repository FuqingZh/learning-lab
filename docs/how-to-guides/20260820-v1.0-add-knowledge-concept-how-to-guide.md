# Add or Update a Knowledge Concept

Version: v1.0
Date: 2026-08-20

## Goal and scope

Add one durable concept, connect it to the existing dependency graph, link only
real learning evidence, and refresh every generated view. This procedure is for
promoted transferable concepts, not every term mentioned during a lesson.

Prerequisites:

- Run commands from the Learning Lab repository root.
- Use Python 3 with the packages in `requirements-dev.txt` installed.
- Preserve current user changes; do not bulk-migrate unrelated notes.
- Read the active [implementation plan](../implementation-plans/20260820-v1.0-knowledge-map-implementation-plan.md)
  for relationship and authority boundaries.

## Procedure

1. Decide whether the item has earned a concept node. It should have a reusable
   definition, a meaningful dependency or distinction, and value beyond one
   repository spelling. Leave incidental product details in the lesson or case
   evidence instead.

2. Create `concepts/<stable-id>.md`. The basename and `id` must match and use
   lowercase hyphenated syntax. Start with the complete shallow schema:

   ```yaml
   ---
   id: example-concept
   title: Example concept
   summary: One concise, implementation-independent definition.
   kind: foundation
   tracks:
     - scientific-ai-platforms
   case_labs: []
   prerequisites: []
   enables: []
   contrasts_with: []
   related: []
   lessons: []
   records: []
   ---
   ```

3. Add only typed relationships you can justify:

   - `prerequisites`: required prior understanding;
   - `enables`: a capability made materially easier or possible;
   - `contrasts_with`: a deliberate confusion boundary;
   - `related`: a useful association that is not a dependency.

   Write every concept target as a quoted vault-root link, for example
   `"[[concepts/partial-failure]]"`. The validator normalizes it to a stable ID
   while Obsidian can use the same property as a graph edge.

   Every target must already exist. Keep `related` sparse. Do not add both
   directions merely to make the picture denser; generated views already expose
   incoming relationships.

4. Add a track only when it teaches or reuses the concept. Add `case_labs` only
   when a pinned source or existing learning record explicitly supports that
   repository association. The existence of `case-labs/<slug>.md` is not
   membership evidence.

5. Link lessons and learning records with repository-relative paths. Do not set
   mastery directly. If multiple records describe one concept, list only the
   effective record unless their YAML frontmatter has an unambiguous
   repository-relative `supersedes` chain.

6. Validate the source model before generating views:

   ```bash
   python3 scripts/build-knowledge-map.py validate
   ```

   Fix every dangling target, unknown kind, unknown track or case lab, missing
   evidence path, record ambiguity, or prerequisite cycle. Do not weaken the
   validator to accept uncertain data.

7. Regenerate both projections:

   ```bash
   python3 scripts/render-knowledge-map-markdown.py
   python3 scripts/render-knowledge-map-site.py
   ```

8. Run the canonical gate:

   ```bash
   bash scripts/check-structure.sh
   git diff --check
   ```

## Expected result

- The concept appears in `maps/concepts/<stable-id>.md`.
- Applicable track and explicitly evidenced case-lab views include it.
- `site/index.html` can find it through search and the relevant view selector.
- Its mastery color agrees with the effective learning record.
- A second generation leaves `maps/` and `site/index.html` unchanged.

## Recovery

If validation fails, repair the canonical concept or evidence link and rerun the
generator. Never repair `maps/` or `site/index.html` directly; those files are
reconstructable projections. If the correct relation or effective record cannot
be established, leave the field empty and preserve the uncertainty in the
lesson or learning record rather than guessing.
