# Add or Update an Evidence-backed History Dossier

Version: v1.3
Date: 2026-08-24

## Goal and scope

Add one auditable history dossier that helps a learner distinguish a concept's
documented development from its present-day professional meaning. This guide
governs `histories/<stable-id>.md`; it does not create a canonical concept,
rewrite a concept definition, or change learning-state evidence.

Prerequisites:

- Run commands from the Learning Lab repository root.
- Read the active [history implementation plan](../implementation-plans/20260824-v1.2-evidence-backed-knowledge-history-plan.md).
- Read the active [evidence-graph delivery plan](../implementation-plans/20260824-v1.3-typescript-explorer-and-evidence-graph-plan.md)
  when a dossier should appear in the interactive evidence network.
- Apply both the canonical terminology gate and historical evidence gate in
  `AGENTS.md`.
- Preserve unrelated user changes and generated projections.

## Evidence review before authoring

1. State the bounded teaching question first: for example, when a term was
   documented, how a problem was formalized, or how a standard later adopted a
   property. Do not begin with a presumed inventor or origin story.

2. Collect direct HTTPS links for every milestone. Prefer a primary document
   for what that document said or did. Use a scholarly secondary source when
   interpreting historical context, motive, disagreement, or a priority claim.
   Later standards and professional documentation can establish later adoption
   but cannot establish undocumented original intent.

3. Separate milestone kinds: `terminology`, `problem`, `formalization`,
   `adoption`, `popularization`, `revision`, and `critique`. Do not collapse an
   algebraic use, a protocol property, and an application mechanism merely
   because they share a term.

4. Review the wording claim by claim. `first`, `invented`, `coined`, and
   similar priority language require a source that specifically establishes
   priority. An actor's motive requires a contemporary primary source or
   explicit scholarly analysis. Otherwise use bounded language such as
   `documented in` or `used by`.

5. Record competing lineages, disagreement, and missing evidence in the
   dossier. If a source does not support the sentence, fail closed: omit it or
   qualify it. Never add invented scenes, dialogue, motives, causal links, or
   a single-hero narrative to fill a gap.

6. Recheck any linked canonical concept under the terminology gate. Historical
   use is not evidence that a term has the same established modern meaning.
   A lesson-linked dossier may remain outside `concepts/`.

## Author the dossier

1. Create `histories/<stable-id>.md` with the v2 frontmatter contract when its
   evidence should enter the network. The dossier ID and filename must be
   stable lowercase hyphenated IDs.
   Include every required top-level field: `schema_version`, `id`, `title`,
   `summary`, `concepts`, `lessons`, `tracks`, and `milestones`. Link at least
   one existing concept or lesson.

2. Give each milestone a stable ID, a required year, a permitted kind, actors,
   a bounded claim, a sorted nonempty `subjects` list of canonical concept IDs,
   a sorted nonempty `boundaries` list, and one or more sources. Use `primary` or
   `scholarly-secondary` source roles, and only the allowed source kinds.
   Every v2 source occurrence also needs a precise nonempty `locator`.
   Leave `month` and `day` as `null` when the source does not establish them;
   never fabricate date precision.

   Schema v1 remains readable for existing history timelines, but it emits no
   evidence-network nodes or edges. Shared wording, dossier membership, or a
   repeated source URL never implies a concept relationship; only explicit
   milestone `subjects` do.

3. Use all required Markdown headings:

   ```markdown
   ## Historical setting
   ## What the sources establish
   ## What the sources do not establish
   ## Development
   ## Modern boundary
   ```

   The body may explain uncertainty, but it must not add an uncited milestone
   claim absent from the frontmatter.

4. Design the teaching use as one historical increment only: documented
   setting, a prediction prompt that is not attributed to the actor, source
   reveal, and a modern-boundary contrast. Assess understanding with
   `explain-back` or `fresh-case-transfer`, never date recall.

## Validate and recover

Run the history contract checks before changing generated views:

```bash
python3 scripts/build-knowledge-history.py validate
python3 scripts/build-knowledge-history.py normalized-data
python3 scripts/build-knowledge-history.py normalized-evidence-data
python3 tests/knowledge-history/test_validation.py
```

Then run the repository gate:

```bash
bash scripts/check-structure.sh
git diff --check
```

Structural validation checks schema and references; it cannot prove that a
source supports a sentence, establishes priority, or reveals motive. Keep the
manual evidence review with the change. If validation fails, repair the dossier
or its link. If the evidence remains uncertain, preserve that uncertainty or
leave the milestone out; do not weaken the validator or edit generated output
directly.
