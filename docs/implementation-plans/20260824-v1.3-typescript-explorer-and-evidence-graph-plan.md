# v1.3 TypeScript explorer and evidence graph implementation plan

Version: v1.3  
Date: 2026-08-24  
Status: approved for execution; Slice 0 pending

## Outcome

Replace the monolithic browser implementation embedded in
`scripts/render-knowledge-map-site.py` with a maintainable TypeScript frontend
without moving canonical knowledge, history, or learning-state semantics into
the browser.

The delivered site remains a deterministic, self-contained
`site/index.html` that works from GitHub Pages and by opening the file directly.
After frontend parity is complete, add a separate evidence graph so sources
such as EWD123 can appear as first-class, auditable nodes connected through the
specific historical claims they support.

The migration is delivered as two independently reversible pull requests:

1. **PR A — TypeScript frontend parity:** preserve all current behavior while
   replacing the browser implementation.
2. **PR B — Evidence graph:** add source/claim relationships without changing
   the semantics of the canonical concept graph.

## Why this boundary

The repository already has three deterministic domain engines:

- `scripts/build-knowledge-map.py` owns present-day concept validation and
  typed concept relationships;
- `scripts/build-learning-state.py` owns append-only learning-state
  projection; and
- `scripts/build-knowledge-history.py` owns evidence-backed historical
  dossiers.

TypeScript reduces risk in UI state, URL routing, component composition, and
graph interaction. It does not replace those engines. The frontend consumes
their normalized JSON at build time and never reparses Markdown/YAML or derives
mastery, due state, historical membership, or terminology validity.

The repository may reuse the organizational pattern demonstrated by
`mattpocock/dictionary-of-ai-coding`—one entry per file, deterministic
generation, and CI freshness—but that repository is not a reusable dynamic
graph frontend. A graph library is adopted only after a bounded spike proves
that it removes more complexity than it adds.

## Preserved contracts

PR A must preserve all of the following:

1. Markdown/YAML remains the durable source of truth.
2. The three Python normalized-data commands remain the sole domain authority.
3. `python3 scripts/render-knowledge-map-site.py` remains a supported site
   generation entrypoint, even if it becomes a thin orchestrator.
4. The final publication artifact remains `site/index.html`.
5. The site performs no browser-time network fetch and loads no CDN resource.
6. The site works through both `file://` and the GitHub Pages repository
   subpath.
7. Existing URL hashes and state restoration remain compatible.
8. Global, track, case-lab, focal, Today, Continue, Recall, relationship, and
   history views remain available.
9. Keyboard operation, visible focus, reduced motion, mobile layout, safe
   external links, and the non-visual concept list remain supported.
10. `site/` remains the only Pages upload boundary.

PR B must additionally preserve the meaning of `normalized_graph_v1`. Sources,
claims, and historical milestones do not become prerequisite, enablement,
contrast, or related concept edges.

## Non-goals

- Rewriting the canonical Python builders in TypeScript.
- Parsing repository Markdown or YAML in the browser.
- Adding a backend, database, API, authentication layer, or runtime service.
- Making Vite, React, React Flow, Dagre, or any other library mandatory before
  the spike passes.
- Keeping the old and new browser implementations active indefinitely.
- Inferring concept or evidence relationships from prose, shared URLs, or
  source co-occurrence.
- Promoting `program`, `process`, `service`, or any other lesson phrase into
  `concepts/` without passing the canonical terminology gate.
- Changing the learning-state event schema merely to support the new UI.

## Target architecture

```text
concepts / histories / learning-state / lessons
                    |
                    v
       canonical Python validators/builders
                    |
                    v
   GRAPH + LEARNING_STATE + HISTORY JSON
                    |
                    v
         TypeScript presentation modules
                    |
                    v
       self-contained site/index.html
                    |
           +--------+--------+
           |                 |
        file://         GitHub Pages
```

After PR B:

```text
Concept <-- about -- Claim/Milestone -- cites_as_evidence --> Source
```

The concept graph and evidence graph are separate projections that may share a
concept identifier. They do not share edge semantics.

## Repository layout after PR A

The spike may revise names, but the stable boundary should resemble:

```text
frontend/

  src/
    contracts/
```

## Delivery slices

### Slice 0 — isolate the current content checkpoint

The worktree currently contains learner-authored or learning-session content,
history material, and a regenerated site. These paths must not be mixed with
the frontend migration.

Actions:

1. Record the exact branch and HEAD.
2. Validate the existing content as one independent checkpoint.
3. Commit that content separately. PR A must branch from the commit containing
   the validated learner/history inputs and their synchronized generated site,
   not from an earlier HEAD.
4. Do not use `stash`, `reset`, or an all-files frontend commit to absorb the
   content changes.
5. Start PR A only from a clean migration worktree.

If repository authority prevents creating the content checkpoint, PR A is
blocked until the content owner can create an independent commit. A file list
or digest record is audit evidence, not a Git snapshot from which a branch can
be derived. If a temporary local checkpoint commit is explicitly authorized,
record its SHA together with `git diff --name-only`, SHA-256 digests for all
three canonical normalized-data serializations, and the `site/index.html`
digest; derive the migration branch from that commit and do not publish it as a
content decision without the content owner's approval.

Exit condition: `git status --short` is clean in the migration worktree and the
exact baseline commit is recorded in the PR.

Rollback: no frontend code exists in this slice; content follows its normal
revert path.

### Slice 1 — freeze cross-language and browser contracts

Add executable parity tests before changing the production renderer.

The baseline must cover:

- exact equality of embedded `GRAPH`, `LEARNING_STATE`, and `HISTORY` with the
  three normalized-data commands;
- deterministic output across two clean renders;
- absence of browser `fetch`, CDN scripts, remote stylesheets, and remote
  runtime assets;
- direct `file://` startup;
- GitHub Pages repository-subpath startup, simulated locally by mounting the
  repository root beneath `/learning-lab/` and executing the page at
  `/learning-lab/site/` in the browser harness;
- current hash routes, including concept, history, Today, Continue, and Recall;
- search, track selection, relationship selection, history timeline, safe
  source links, and empty states;
- keyboard-only operation and visible focus;
- mobile viewport and reduced-motion behavior; and
- a structured DOM fallback containing all visible concepts.

Exit condition: these tests pass on the recorded baseline without changing the
published implementation.

Rollback: revert only the new tests and fixtures.

### Slice 2 — bounded TypeScript graph spike

Build two read-only projections over the same fixed normalized-data fixture:

1. the current native DOM/SVG graph behavior; and
2. TypeScript with React Flow and Dagre as the provisional candidate.

The spike is not the production migration. It answers the following questions
with executable evidence:

- Can a learner complete search -> result -> node -> typed relationship ->
  source using only the keyboard?
- Does the candidate expose meaningful node names and relationship direction
  to the accessibility tree?
- Is layout deterministic for identical input?
- Does prerequisite/enablement determine rank without treating `related` or
  `contrasts_with` as hierarchy?
- What happens at 100, 300, and 1000 synthetic concept nodes?
- Can the build produce one offline HTML file with no runtime fetch or CDN?
- Does that file work from `file://` and a Pages repository subpath?
- What are the dependency count, compressed output size, clean build time, and
  amount of repository-owned graph interaction code?

Both candidates use the same checked-in fixtures and the same Node and Chrome
versions. Record the host CPU, memory, operating system, Node version, Chrome
version, exact commands, and raw measurements. A repository script owns
fixture generation, line counting, gzip sizing, repeated build timing, and
browser timing so the decision can be rerun.

#### Go/no-go decision

The following are hard gates. Any failure selects native DOM/SVG + strict
TypeScript:

| Hard gate | Mechanical decision |
| --- | --- |
| Self-contained delivery | Output is exactly one HTML file and contains no runtime `fetch`, CDN, remote stylesheet, module import, or remote asset dependency. |
| Local opening | Browser harness passes from `file://`. |
| Pages path | Browser harness passes from the simulated `/learning-lab/site/` path with all supported hashes. |
| Keyboard and accessibility | The documented search -> result -> node -> typed relationship -> source path is operable without a pointer; interactive nodes appear by accessible name and role. |
| Determinism | Three clean builds of identical inputs have the same SHA-256 digest. |
| Scale safety | The 1000-node fixture renders without a console exception within 5 seconds and a filter update settles within 500 ms on the recorded host. |

React Flow + Dagre is selected only if it passes every hard gate and all of the
following bounded-cost tests against the native TypeScript candidate:

- repository-owned graph/layout/accessibility source lines, counted as
  nonblank noncomment TypeScript/TSX lines under the two candidate graph
  directories, are at most 70% of the native candidate;
- gzip size of the single-file candidate is at most twice the native candidate
  and at most 750 KiB;
- median clean build time across five runs is at most three times the native
  candidate and at most 15 seconds; and
- direct production dependencies are no more than six.

These thresholds decide this repository's v1 migration; changing them requires
updating this plan with measurements and rationale before the selection.

If it fails the single-file, offline, accessibility, determinism, or
maintenance boundary, keep the existing native DOM/SVG rendering model and
move it into strict TypeScript modules instead. Cytoscape.js is deferred unless
large-graph algorithms or network-analysis operations become demonstrated
requirements.

The spike decision and measurements are recorded in this plan before Slice 3
begins.

Rollback: delete the spike directory and dependency changes. Production output
has not switched.

### Slice 3 — establish the TypeScript build boundary

Add the selected TypeScript toolchain without changing the production site
renderer.

Requirements:

- a committed lockfile and exact reproducible install;
- strict TypeScript checking;
- explicit `frontend:check`, test, and site-build commands;
- build-time injection of canonical JSON;
- no browser parsing of repository sources;
- temporary build output outside `site/` until the atomic switch;
- no second long-lived interpretation of canonical schema; and
- Pages workflow changes only after the toolchain passes locally.

The supported Python site command gains an explicit runtime prerequisite at
the atomic switch: Node.js 22.x and dependencies installed by `npm ci`. A
missing or wrong Node runtime, or missing installed dependencies, must fail
with one deterministic diagnostic that names the required version and the
`npm ci` recovery command. It must not download dependencies implicitly.

Exit condition: a clean clone can install, type-check, test, and produce a
candidate artifact while the checked-in `site/index.html` still comes from the
old renderer.

Rollback: revert the toolchain commit and retain the Python-only Pages path.

### Slice 4 — atomic frontend parity switch

Move all current browser behavior to the TypeScript implementation in one
reviewable switch.

The Python entrypoint may remain as a thin adapter that:

1. invokes or imports the canonical builders;
2. serializes their normalized JSON;
3. invokes the frontend build; and
4. verifies/writes the final `site/index.html`.

It must not retain a second embedded browser implementation.

Exit conditions:

- all Slice 1 contracts pass against the TypeScript output;
- the old monolithic HTML/JavaScript template is removed;
- only one production frontend path remains;
- two renders are byte-identical; and
- generated drift checks understand the new build path.

Rollback: revert the atomic switch commit. Canonical builders and content remain
unchanged.

### Slice 6 — define `normalized_evidence_graph_v1` in PR B

After frontend parity, extend the history domain with a separate deterministic
evidence projection. This is an explicit history authoring schema upgrade, not
an unversioned optional-field change.

History schema v2 is introduced alongside continued read support for v1:

- every v2 milestone adds required `subjects`, a sorted nonempty list of
  canonical concept IDs;
- every v2 source occurrence adds required nonempty `locator`, describing the
  section, page, fragment, or other evidence location;
- v1 dossiers remain valid for the existing normalized history projection but
  do not emit concept evidence edges unless migrated to v2; and
- a v2 dossier fails closed when a subject concept or locator cannot be
  validated.

Source identity is `source-` plus the first 16 hexadecimal characters of
SHA-256 over a canonical HTTPS URL. Canonicalization lowercases scheme and
host, removes the default HTTPS port and fragment, and preserves path and
query. The original occurrence URL and locator remain on the citation edge.
Occurrences with one source identity must agree on title, publisher, and kind;
conflicting metadata or an ID collision fails closed.

Minimum node kinds:

- `concept`: an existing canonical concept identifier;
- `claim` or `milestone`: a specific auditable historical assertion; and
- `source`: a citable information resource.

Minimum edge kinds:

- `about`: claim/milestone -> concept;
- `cites_as_evidence`: claim/milestone -> source; and
- `contained_in`: milestone -> dossier.

Source occurrence metadata such as `role` and `locator` belongs on the
`cites_as_evidence` edge because one source can play different roles for
different claims. A stable source ID is derived from a canonical identifier
under a documented collision and metadata-consistency policy.

Each milestone that appears in the evidence graph declares explicit subjects.
Shared wording, a shared dossier, or a shared URL never creates an edge.

For the EWD123 pilot, the documented distinction may connect to canonical
`program` and `process` concepts only after both pass the terminology gate. It
must not connect to `service` unless a separately cited milestone supports that
claim.

Exit conditions:

- normalized output is deterministic and JSON-compatible;
- all referenced concepts, dossiers, milestones, and sources resolve;
- duplicate or conflicting source metadata follows an explicit fail-closed
  rule;
- evidence roles and locators survive normalization; and
- `normalized_graph_v1` is byte-for-byte unchanged for the same concept input.

All v2 dossier migrations, schema/builder changes, generated site data, and the
evidence UI belong to PR B's recorded atomic commit set. Rollback reverts those
inputs and code together so the pre-PR v1-only validator never encounters v2
files. The present concept graph and v1 historical timelines then continue to
work.

### Slice 7 — evidence-network UI and delivery

Add an explicit view selector for concept relationships versus evidence
lineage. The evidence view renders concept, claim/milestone, and source nodes
with visually and textually distinct edge types.

Selecting a source shows:

- title, creator/publisher, date when known, and stable identifier;
- the claim or milestone it supports;
- source role and locator;
- a safe direct HTTPS link; and
- boundaries the dossier says the source does not establish.

The evidence view remains usable as a structured list when the spatial graph
is unavailable. Recall mode must not accidentally reveal a hidden modern
definition through source-node labels.

Exit condition: EWD123 can be reached from its supported program/process claim,
the relationship is auditable in both directions, and no unsupported service
edge appears.
