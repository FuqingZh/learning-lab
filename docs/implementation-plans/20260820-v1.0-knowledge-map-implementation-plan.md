## Goal

Add a durable knowledge dependency model to Learning Lab so every promoted
concept can be placed in context, related to multiple tracks and repository
case labs, overlaid with demonstrated mastery, and explored through generated
Markdown, a self-contained local frontend, or Obsidian.

The result must mechanically answer:

- What must be understood before this concept?
- What does it enable, resemble, or contrast with?
- In which tracks and repository case labs has it been applied?
- Which lesson and mastery evidence support it?
- Can the same source be viewed globally, by track, by repository, or around one
  focal concept without duplicating its definition?

## Settled decisions

1. Learning Lab owns one knowledge graph with multiple filtered views. Tracks
   and repositories do not own independent copies of shared concepts.
2. Markdown concept files plus validated YAML frontmatter are the durable source
   of truth. Generated maps and the frontend are projections.
3. Repositories are case laboratories, not the top-level knowledge taxonomy. A
   concept may link to multiple case-lab hub notes.
4. `CURRICULUM.md` owns recommended teaching order; prerequisite edges own
   conceptual dependency. Neither replaces the other.
5. `learning-records/` owns demonstrated personal state. Concept files do not
   acquire a hand-maintained mastery flag; generated views derive it from linked
   records.
6. The baseline frontend is static, offline, and needs no backend, domain, or
   external CDN. A localhost static server is only a browser fallback.
7. Obsidian is a replaceable reader over the same Markdown, properties, and
   links. Its configuration and plugins are not correctness dependencies.
8. Existing curricula, lessons, records, and glossary content migrate
   incrementally. The pilot does not authorize bulk rewriting or deletion.

## Non-goals

- Building a server, database, authentication layer, hosted service, or editor.
- Replacing bounded lessons with one-term notes.
- Turning every mentioned word, class, table, or CLI flag into a graph node.
- Inferring semantic relationships automatically from prose.
- Making Obsidian-specific syntax or a plugin the only readable form.
- Publishing the frontend to a public URL in the initial implementation.

## Authority and component boundaries

| Component | Boundary it owns |
| --- | --- |
| `concepts/*.md` | One canonical definition and typed outbound relationships per concept |
| `case-labs/*.md` | Thin hub for one repository used as case evidence, not product documentation |
| `learning-records/<track>/*.md` | Demonstrated learner state and evidence |
| `lessons/<track>/*` | Reusable teaching artifact linked but not embedded in the graph schema |
| `tracks/<track>/CURRICULUM.md` | Pedagogical order and track progression |
| `maps/` | Generated Markdown navigation and typed Mermaid projections |
| `site/` | Generated self-contained interactive projection |
| `scripts/build-knowledge-map.py` | Parse, validate, derive state, and generate deterministic views |
| `scripts/check-structure.sh` | Repository-wide structural and generated-drift gate |

## Concept contract

Each concept is one Markdown file whose basename equals its stable `id`. The
schema stays shallow so Obsidian Properties and ordinary YAML parsers can read
it.

```yaml
---
id: idempotency
title: Idempotency
summary: Repeating one logical operation preserves its intended final effect.
kind: foundation
tracks:
  - scientific-ai-platforms
case_labs: []
prerequisites:
  - "[[concepts/logical-operation]]"
  - "[[concepts/partial-failure]]"
  - "[[concepts/side-effect]]"
enables: []
contrasts_with:
  - "[[concepts/response-equality]]"
related:
  - "[[concepts/operation-scope]]"
lessons: []
records:
  - learning-records/scientific-ai-platforms/0016-idempotency-foundations-mastered.md
---
```

Required scalar fields are `id`, `title`, `summary`, and `kind`. Concept
relationship fields contain quoted `[[concepts/<stable-id>]]` links so Obsidian
can render the source graph; validation normalizes them back to stable IDs.
Evidence fields contain repository-relative paths. Unknown extension keys are
preserved only when their values are deterministic JSON-compatible data and are
ignored unless a consumer declares them. YAML field order is not authoritative.

### Relationship semantics

| Relationship | Meaning | Constraint |
| --- | --- | --- |
| `prerequisites` | Must be understood before the source concept | Target exists; prerequisite graph is acyclic |
| `enables` | Capability made materially easier or possible | Target exists; reverse prerequisite need not be duplicated |
| `contrasts_with` | Deliberate distinction from an easily confused concept | Target exists; rendered bidirectionally |
| `related` | Useful non-dependency association | Target exists; kept sparse to limit noise |
| `tracks` | Tracks that teach or reuse the concept | Directory exists under `tracks/` |
| `case_labs` | Repository cases where the concept is explicitly evidenced | Slug resolves to `case-labs/<slug>.md`; a hub alone does not justify membership |
| `lessons` | Reusable teaching artifacts | Repository-relative target exists |
| `records` | Evidence from which status is derived | Target exists and has a recognized state |

Declare `contrasts_with` and `related` once per pair. Do not duplicate
`A enables B` when `B prerequisites A` already expresses the same dependency;
incoming relationships are derived by the views.

The initial recognized kinds are `orientation`, `foundation`, `mechanism`,
`pattern`, and `boundary`. New kinds require an explicit schema and view
decision.

## Mastery derivation

The generator derives one display status per concept:

```text
no linked record                         -> not-started
latest effective record is developing   -> developing
latest effective record is mastered     -> mastered
```

Existing filenames ending in `-developing.md` or `-mastered.md` are accepted
for the pilot. Only a repository-relative `supersedes` value in record YAML
frontmatter is machine-readable precedence; an ordinary prose link does not
participate in state resolution. If multiple listed records have no explicit
precedence, or share a date without it, resolution fails closed. Pilot concepts
therefore list only the effective record when existing history lacks metadata.
Glossary or lesson existence never implies mastery.

## Normalized graph v1

Parsing and validation produce one stable `normalized_graph_v1` model consumed
by every renderer. It contains:

- `nodes`, sorted by `id`, with `id`, `title`, `summary`, `kind`, `path`, sorted
  `tracks`, sorted `case_labs`, `relationships` containing the four sorted typed
  concept lists, sorted `lessons`, sorted `records`, and
  `mastery: {status, effective_record}`, plus `extensions` containing only
  recursively canonicalized JSON-compatible unknown metadata;
- `edges`, sorted by `(source, type, target)`, with exactly `source`, `target`,
  and `type`;
- `case_labs`, sorted by slug, with hub title/path and directly associated
  concept IDs; contextual one-hop membership is a renderer projection and never
  written back as direct membership; and
- repository-relative POSIX paths only, with no checkout, vault, or hosted base
  URL embedded.

The generator exposes this model to later renderers through one importable build
function or one canonical JSON serialization. Markdown and frontend renderers
must not reparse concept files or independently derive mastery. Canonical JSON,
when emitted, uses stable key and list ordering so equality and generated drift
are mechanically decidable.

## Generated views

All views consume the same validated normalized graph:

1. `maps/README.md`: entrypoint and legend.
2. `maps/overview.md`: bounded global spine of orientation and foundation nodes.
3. `maps/tracks/<track>.md`: direct nodes plus one-hop prerequisites.
4. `maps/case-labs/<repository>.md`: strict membership followed by one-hop
   contextual dependencies.
5. `maps/concepts/<id>.md`: focal relationships, evidence, and case labs.
6. `site/index.html`: an interactive spatial graph with global and track lenses,
   search, focal concept inspection, typed relationships, and mastery cues.

Generated views carry a warning and regeneration command. They are never edited
as a second authority, and generation must be deterministic and idempotent.

## Obsidian compatibility

- Open the repository root directly as a vault; conversion is unnecessary.
- Concept bodies use ordinary Markdown and frontmatter uses shallow valid YAML.
- Typed concept relationships use quoted vault-root Wikilinks in frontmatter,
  allowing Obsidian Global and Local Graph to connect the canonical concept
  notes without making Obsidian the schema authority.
- Generated pages include ordinary relative Markdown links for GitHub,
  Obsidian, and other readers.
- Global Graph and Local Graph are convenience views. Typed relationship names
  remain authoritative in YAML and generated Mermaid because the core Obsidian
  graph does not preserve every edge's domain meaning.
- `.obsidian/` state is optional. If adopted later, volatile workspace state is
  ignored and only intentional shared configuration is versioned.
- Optional Bases may add named list, table, or card views, but the repository
  generator remains the compatibility and correctness boundary.

## Self-contained frontend contract

`site/index.html` contains or references only repository-local generated assets.
Prefer one HTML file with embedded CSS, JavaScript, and graph data. It must not
load a CDN, call an API, or require network access.

It takes the exploratory interaction pattern of Matt Pocock's AI Coding
Dictionary as a reference, without copying its implementation or visual assets.
The graph is the primary surface rather than a dashboard of controls. It
provides:

- a spatial, depth-cued global graph that supports pointer drag rotation and
  wheel/trackpad zoom;
- track lenses over the same graph, rather than separate graph authorities;
- text search and hash-addressable focal concept selection;
- typed relationship and mastery cues with a compact legend;
- keyboard-accessible DOM node selection and a textual relationship panel;
- links to canonical concepts, lessons, and records;
- a useful empty-result state.

Direct `file://` opening is the target. A documented
`python3 -m http.server 8000 --bind 127.0.0.1` from the repository root followed by
`http://localhost:8000/site/` is acceptable, but no formal URL is required.
Serving only `site/` is unsupported because canonical links intentionally point
back to sibling concept and evidence directories. The fallback is a temporary
loopback-only service; hosting remains an independent later decision.

## Implementation slices

### Slice 1: schema, validator, and pilot graph

Predecessors: none.

Affected components: `concepts/`, `case-labs/`,
`scripts/build-knowledge-map.py`, and focused tests or fixtures.

Outcome:

- Implement parsing and the complete validation contract.
- Create a pilot around partial failure, logical operation, side effect,
  operation scope, idempotency key, idempotency, response equality, retry safety,
  and authoritative readback.
- Case hubs are optional in the pilot. A hub or track-anchor statement alone
  does not justify concept membership; `case_labs` remains empty without an
  explicit, pinned case source or existing record that names the repository.
- Link `0016-idempotency-foundations-mastered.md` as the effective record for
  the seven idempotency-family nodes it explicitly demonstrates, and link only
  the mastered system-success record for authoritative readback. Do not create
  mastery evidence merely to satisfy the graph.
- Do not convert unrelated glossary terms or rewrite lessons.

Verification:

- Build succeeds on pilot data.
- Invalid fixtures reject duplicate IDs, basename mismatch, dangling edges,
  unknown tracks/case labs, missing evidence, invalid kinds, and prerequisite
  cycles.
- A second generation produces no diff.

Acceptance: every pilot concept is independently readable, and `idempotency`
derives `mastered` from the existing record without a concept status field.

Durable evidence: concept files, case hubs, generator, and executable tests.

### Slice 2: generated Markdown views

Predecessor: Slice 1 normalized schema.

Affected components: `maps/` and generator Markdown renderers.

Outcome: generate overview, track, case-lab, and focal views; keep strict case
membership separate from contextual dependencies; render edge type and mastery
consistently.

Non-goal: interactive browser behavior.

Verification: relative links resolve, warnings identify sources and command,
and repeated generation is byte-identical.

Acceptance: a reader can navigate from the entrypoint to idempotency, its
prerequisites, evidence, and any explicitly supported case labs without
repository search.

### Slice 3: self-contained interactive frontend

Predecessor: Slice 1 normalized graph. It may run in parallel with Slice 2 after
that interface is stable.

Affected components: `site/index.html` rendering and frontend smoke checks.

Outcome: implement the offline spatial-explorer contract without backend or
runtime network dependencies. The normalized graph and generated Markdown stay
unchanged; this revision replaces the earlier control-dashboard/SVG-grid
projection only.

Non-goals: public deployment, concept editing, authentication, and layout
optimization for thousands of nodes.

Verification:

- Static inspection rejects remote scripts, stylesheets, fonts, images, fetches,
  and API dependencies.
- Embedded data equals the validated normalized pilot graph.
- Browser smoke verifies graph execution, DOM node/evidence availability,
  hash-addressed focal selection, and canonical links.
- Direct file opening is checked; localhost fallback is documented if needed.

Acceptance: the graph is usable offline from one generated entrypoint, feels
like an explorable knowledge space rather than a static grid, and has a
non-visual textual relationship path.

### Slice 4: repository integration and authoring workflow

Predecessors: Slices 1-3.

Affected components: `README.md`, relevant track entrypoints,
`scripts/check-structure.sh`, and authoring guidance.

Outcome:

- Link the map from the workspace entrypoint.
- Make the existing gate validate schema and generated drift.
- Document how a lesson promotes a concept, links evidence, rebuilds views, and
  checks the repository.
- Preserve the current track migration and unrelated uncommitted work.

Verification: `bash scripts/check-structure.sh`, `git diff --check`, and a check
that every newly introduced Markdown link resolves.

Acceptance: a future teaching session has one repeatable command path for adding
or updating a concept and refreshing every view.

### Slice 5: incremental migration decision

Predecessor: successful use of the pilot in at least one later learning session.

Evaluate usefulness, authoring cost, edge quality, and Obsidian navigation before
migrating existing glossary entries. This slice does not start automatically;
bulk migration requires fresh approval or accepted pilot evidence.

## Dependency and review graph

```text
plan
  -> Slice 1 schema and pilot
       -> Slice 2 Markdown views ----\

```

Review splits follow the same boundaries. Parallel writers own disjoint files;
the integrating writer owns shared entrypoints only after reading the actual
generated contract.

## Risks and containment

| Risk | Containment |
| --- | --- |
| Large graph becomes unreadable | Bounded global, filtered, and focal views; sparse `related` edges |
| Track or repository copies drift | Store each concept once and generate projections |
| Mastery conflicts with records | Derive only from explicit record links and fail on ambiguity |
| Obsidian reduces portability | Ordinary Markdown and validated YAML; Obsidian remains optional |
| Generated files become edited authorities | Warnings and deterministic drift validation |
| Browser silently requires internet | Reject remote assets and runtime fetches |
| Current uncommitted migration is damaged | No deletion, rename, staging, or unrelated rewriting |
| Schema grows without control | Preserve unknown metadata but explicitly approve consumed fields/kinds |

## Compatibility and migration

The initial change is additive. Existing paths and teach-workspace discovery
remain valid. Existing records may be linked without frontmatter; filename-based
state is a bounded pilot compatibility path. Its retirement condition is an
accepted record metadata contract after real use.

The generator reads repository-relative paths and emits relative links. It must
not encode the absolute workspace path, Obsidian vault name, hosted base URL, or
source-repository checkout path.

## Rollback and cleanup

Before Slice 4, rollback deletes only new `concepts/`, `case-labs/`, `maps/`,
`site/`, and knowledge-map generator artifacts. Existing lessons and records
need no restoration because the pilot does not replace them.

After Slice 4, rollback additionally removes only the knowledge-map invocation
from `scripts/check-structure.sh`. Generated artifacts are reconstructable and
must be regenerated rather than repaired manually.

## Final verification

The initial implementation completes only when:

1. Pilot schema and references validate fail-closed.
2. Mastery is derived from repository evidence.
3. Markdown and HTML projections are deterministic and have no remote runtime
   dependencies.
4. Global, track, strict case-lab, contextual case-lab, and focal views agree on
   one normalized graph.
5. Obsidian opens the repository without conversion while correctness remains
   independent of Obsidian and plugins.
6. `bash scripts/check-structure.sh` and `git diff --check` pass.
7. No existing learning material is lost, duplicated as new authority, or
   silently reclassified.
