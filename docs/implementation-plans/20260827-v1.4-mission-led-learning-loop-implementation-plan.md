# v1.4 Mission-led Learning Loop Implementation Plan

Version: v1.4
Date: 2026-08-27
Status: structurally implemented; model-backed reliability evaluation remains incomplete

## Outcome

Make the personal learning loop select one bounded, mission-linked lesson from
the learner's demonstrated capability and trusted curriculum context, while
preserving interruption-safe resume and review cues without letting a concept
scheduler own curriculum progression.

When complete:

- the tutor reads the learner contract before choosing a lesson;
- learning records are the authority for reviewed demonstrated capability;
- session events remain append-only raw observations and own durable resume;
- review dates are explicitly labeled cues derived from session history;
- a resume can identify a lesson unit or concept without pretending they are
  the same object;
- assisted work cannot independently promote capability or lengthen a success
  interval;
- the graph remains a professional-concept navigation structure rather than a
  complete course-authoring schema; and
- repository-owned cases and scorecard provenance bound any future claim of
  model teaching reliability.

This plan is the execution successor for the pedagogical-selection,
learner-state-ownership, and resume portions of the
[v1.1 Ambient Learning plan](20260821-v1.1-ambient-learning-implementation-plan.md).
The existing v1 runtime remains supported until the relevant slice below is
implemented and verified.

## Accepted Architecture Decisions

### D-1. Pedagogical selection is mission-led

The tutor selects one primary lesson win from:

1. `MISSION.md` and `NOTES.md`;
2. reviewed demonstrated capability;
3. the active track curriculum and trusted resources;
4. the latest durable resume;
5. relevant review cues and concept relationships; and
6. the learner's current request or repository case.

Due state is an input to that decision, not an unconditional queue. The tutor
must state the lesson win and stopping condition before teaching.

### D-2. Learning records own reviewed capability

`learning-records/<track>/` remains the durable authority for what the learner
has demonstrated. Record prose explains the capability and evidence. Structured
record metadata, introduced incrementally, supplies machine-readable capability
state.

Session event outcomes are raw observations. They can create review cues and a
candidate for record promotion, but they do not directly become authoritative
capability.

### D-3. Session events own observations and resume

`learning-state/sessions/` remains append-only. Existing v1 events are never
rewritten. A v2 event can identify the next unit as a lesson, concept, or track
orientation and records an explicit prose checkpoint. Empty evidence continues
to mean no observed capability check.

### D-4. The scheduler owns review cues only

Review intervals are transparent, replaceable suggestions. They do not claim
automatic spaced-review delivery or determine the next curriculum unit.

Only an unassisted passing observation may advance a success interval. An
assisted pass, `partial`, or `miss` schedules a near-term cue and cannot promote
reviewed capability by itself.

### D-5. The knowledge graph is not the course inventory

`concepts/` owns established professional concepts and typed relationships.
Curricula and lessons own teachable units. A lesson may include several concepts
or teach a transferable capability that is not yet a canonical graph node.

No concept or glossary term is promoted merely to make a lesson schedulable.

### D-6. Learning Lab is a documented Teach extension

The marked personal workspace, track-nested records, semantic lesson names,
Markdown teaching artifacts, histories, graph, and site are preserved. The
repo-local tutor documents how it implements Teach outcomes and where its
durable formats differ. This plan does not bulk-convert lessons to numbered
HTML or flatten track directories.

## Authority And Data Flow

| Surface | Owner | Consumers |
| --- | --- | --- |
| `MISSION.md` | workspace learning outcome and constraints | tutor selection, curricula |
| `NOTES.md` | personal teaching preferences | tutor behavior |
| Track `CURRICULUM.md` | pedagogical progression | tutor selection, human navigation |
| Track `RESOURCES.md` | trusted current and historical sources | tutor, lessons, histories |
| `learning-records/<track>/` | reviewed demonstrated capability | tutor, graph projection, site |
| `learning-state/sessions/` | raw observations and durable resume | review-cue builder, record-promotion workflow |
| `concepts/` | professional concept definitions and relations | curricula, map, tutor context |
| `histories/` | sourced historical claims | selected lessons, evidence views |
| `maps/` and `site/` | generated projections | learner and reviewer interfaces |

The intended path is:

```text
learner contract + demonstrated capability
  -> bounded lesson selection
  -> curriculum, source, concept, history, and case context
  -> observed evidence and resume event
  -> reviewed capability record and independent review cue
```

## Compatibility Contracts

### Existing learning records

- Existing paths and prose remain valid.
- Existing `developing` or `mastered` filename suffixes remain historical labels
  but do not alone establish the new structured capability state.
- Structured metadata is added only after evidence review; no filename-only bulk
  inference is allowed.
- Superseded records remain traceable.

The record metadata contract introduced by Slice 3 is:

```yaml
---
schema_version: 1
track: scientific-ai-platforms
concepts:
  - idempotency
capability_state: usable
demonstrated_at: "2026-08-19"
assisted: false
evidence_sessions:
  - 20260819T120000+0800-idempotency-fresh-case-transfer
supersedes: []
---
```

Allowed capability states are `encountered`, `familiar`, `usable`, and
`retained`. `evidence_sessions` links the reviewed conclusion to append-only
observations instead of copying their outcome. A record without this metadata
remains readable legacy evidence but does not participate in the new
authoritative capability projection.

### Session event v2

Existing v1 events remain accepted and byte-unchanged. New v2 events use a
neutral event ID that does not claim an evidence check:

```yaml
schema_version: 2
id: 20260827T123000+0800-scientific-ai-platforms-session
started_at: 2026-08-27T12:30:00+08:00
duration_minutes: 12
mode: guided-lesson
track: scientific-ai-platforms
resume:
  unit_kind: lesson
  unit_ref: lessons/scientific-ai-platforms/web-document-browser-and-server.md
  checkpoint: Compare browser navigation with a fresh client-server case.
  summary: Continue the connected document, browser, server, request, and response model.
evidence: []
```

`unit_kind` is one of `lesson`, `concept`, or `track`. `unit_ref` must resolve
to a repository-relative lesson path, known concept ID, or known track ID as
appropriate. `checkpoint` and `summary` are non-empty prose. Evidence retains
the existing per-concept shape.

The normalizer maps a v1 `resume.next` to a legacy concept unit, preserves the
v1 summary, and retains additive `from` / `next` aliases for existing
schema-v1 consumers. It does not invent a lesson reference from prose.

### Review cues

- `partial`, `miss`, and assisted `pass` produce a next-day cue.
- Only unassisted `pass` observations count toward the 1/7/21/60-day success
  intervals.
- Review cues never change reviewed capability.
- `list-due` is renamed or aliased with a user-facing `list-review-cues`
  command; the v1 command remains compatible during migration.

### Terminology

The repository terminology gate remains authoritative for `concepts/` and
`GLOSSARY.md`. Workspace-local explanatory phrases stay in lessons or learning
records unless two independent authoritative sources establish the exact
professional term and meaning. No terminology migration is inferred from
session evidence.

## Non-goals

- Do not build a general course-authoring platform.
- Do not make every lesson or curriculum heading a graph node.
- Do not infer structured capability from legacy filenames alone.
- Do not rewrite append-only v1 session events.
- Do not flatten track directories or bulk-convert Markdown lessons to HTML.
- Do not adopt FSRS before the authority and assisted-evidence boundaries are
  correct.
- Do not claim that a static skill test proves model teaching behavior.
- Do not modify source engineering repositories as part of this learning-loop
  work.

### Slice 7. Run targeted model-behavior evaluation

Predecessors: Slices 1, 2, and 4. Use the Slice 3 projection when available.

Affected components:

- a repository-owned evaluation fixture and scorecard location selected during
  implementation;
- no production learner records or private raw transcripts committed.

Representative cases:

1. A due concept exists but the mission-linked Web lesson resume remains the
   better bounded win.
2. A due retrieval is selected and the tutor does not reveal the answer before
   the learner's attempt.
3. A learner stops before a check and the tutor records structured resume with
   empty evidence.
4. An assisted transfer produces a near-term review cue but no capability
   promotion.
5. A Bioinformatics Systems lesson is selected even though its scientific term
   is not a canonical concept node.
6. The tutor teaches in Chinese, uses the active trusted source, and ends with
   one unaided check.

Evaluation contract:

- freeze model, reasoning effort, tools, fixture, and turn protocol;
- start each run in fresh isolated mutable state;
- repeat cases when variance can change pass/fail;
- score observable behavior only;
- keep authoring cases separate from at least one holdout case;
- report incomplete or mixed results without claiming reliability.

Acceptance:

- the static fixture, state-replay, and scorecard contracts pass before any
  model-backed run;
- all critical behaviors must pass repeated targeted and holdout model gates
  before claiming reliable teaching; otherwise the result remains explicitly
  incomplete or mixed and supports structural completion only.

Durable evidence:

- sanitized fixtures, scorecard schema, aggregate results, limitations, and
  rollout decision.

## Risks And Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Existing dirty learner work is overwritten | Loss of personal state | One writer, path-scoped edits, fresh status and diff before each slice |
| Record frontmatter becomes a second opaque state store | Authority remains duplicated | Prose and metadata live in the same reviewed record; no separate capability file |
| Legacy records silently become retained | Overstated capability | Explicit audit; never infer from filename |
| v2 invalidates append-only history | Loss of provenance | Dual reader; never rewrite v1 events |
| Due rename breaks callers | Compatibility failure | Retain `list-due` alias through migration |
| Graph growth is used to unblock lessons | Terminology gate erosion | Curricula and lessons remain independently selectable |
| Static tests are reported as model reliability | Unsupported claim | Separate behavioral evaluation and scoped completion language |
| Historical framing expands every lesson | Fatigue and loss of bounded win | Include history only when it supports the selected outcome |

## Rollback And Cleanup

- Slice 1 can be reverted as a skill-contract change without touching learner
  evidence.
- Slice 2 preserves the v1 CLI alias and source events; rollback restores the
  previous projection code without data migration.
- Slice 3 metadata is additive. If the projection is withdrawn, records remain
  readable Markdown and the metadata remains auditable.
- Slice 4 is additive dual-schema support; v1 events remain the recovery path.
- Generated maps and site artifacts are regenerated from canonical inputs; do
  not hand-edit them during rollback.
- Evaluation fixtures use isolated temporary learner state and are removed or
  retained only according to the documented evidence policy.
