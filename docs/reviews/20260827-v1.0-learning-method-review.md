## Decision Boundary

This document records a read-only assessment of the workspace learning method:
whether the pedagogical design is sound, whether the current contracts can
carry the mission, and which conclusions are supported by stored evidence.

It distinguishes three authorities:

1. `MISSION.md`, `NOTES.md`, trusted resources, track curricula, and
   demonstrated learner records own pedagogical intent and learner context.
2. Validated schemas, scripts, and the tutor skill own their stated technical
   runtime contracts.
3. Implementation plans guide future changes but do not override current
   learner intent or convert an unobserved model behavior into fact.

When those surfaces disagree, the disagreement must first be classified as a
pedagogical-authority defect, runtime-contract defect, stale projection, or
unsupported observation. An active implementation plan is not automatically
authoritative over all teaching behavior.

This review does not change concepts, lessons, histories, session events,
generated maps, or the tutor skill. It does not authorize concept promotion,
glossary rewriting, session backfill, or implementation. The separate v1.4
plan records the proposed execution path.

## Verdict

The workspace has a strong personal-learning content and evidence architecture,
but its model-facing execution path is not yet mission-led or governed by one
learner-state authority.

The durable boundary is sound: this is a marked personal learning workspace,
separate from source repositories and product authority. Its mission, trusted
resources, teaching preferences, track curricula, evidence-bearing learning
records, case laboratories, terminology gate, and historical evidence gate are
substantial strengths.

The principal defect is not merely a sparse concept graph. The tutor entrypoint
starts from due state, a concept graph, and a concept-shaped resume without
requiring the model to read the mission, teaching notes, trusted resources,
active curriculum, or recent demonstrated-learning records. At the same time,
record-derived mastery and session-derived capability can both appear to answer
what the learner already knows.

A compatible model can validate and write session YAML. Static inspection and
stored YAML do not establish that a model reliably teaches either track as
designed. Reliable execution remains unproven until representative tutoring
cases are run and reviewed.

The 2026-08-27 tutor rewrite removes a fixed three-minute quota and permits a
coherent bounded lesson unit. That is compatible with `NOTES.md`: the notes ask
for small units while explicitly forbidding fragmentation of a connected
framework. The rewrite does not by itself bind learner context, select a
mission-linked win, resolve learner-state ownership, or make lesson resume
structured.

## What Holds

1. The mission targets transferable scientific-systems reasoning, not product
   command recall. Both tracks correctly use repositories as case laboratories.
2. Coverage alone is not mastery. Durable capability requires unaided retrieval
   or transfer on a fresh case; delayed unassisted transfer is an appropriate
   bar for `retained`.
3. `MISSION.md` is concrete, `NOTES.md` expresses clear learner preferences,
   and track resource files record publisher, applicability, checked date, and
   source gaps. These are suitable teaching inputs.
4. Representative learning records contain specific demonstration evidence and
   therefore provide stronger learner-context evidence than filenames alone.
5. Map-first orientation, typed relationships, and repository case views are
   useful navigation and teaching aids. They need not become the curriculum
   scheduler.
6. The terminology and historical evidence gates are appropriate fail-closed
   protections against invented professional jargon and unsupported origin
   stories.
7. `capability_state` and `review_state` are technically separate in the state
   engine, and `list-due` is a caller-date projection rather than a hidden clock.
8. Resume-only events with `evidence: []` correctly avoid inventing capability
   evidence when a learner stops before a check.

## Findings

### F-1. The tutor entrypoint does not bind the learner contract

Teach selects one tangible win from the learner's mission, demonstrated
starting capability, trusted sources, and current preferences. The current
tutor skill instead begins with normalized state, due state, the concept graph,
and the latest resume.

It does not require reading `MISSION.md`, `RESOURCES.md`, `NOTES.md`, the active
track curriculum and resource index, or recent relevant learning records before
selecting the lesson. Consequently, Chinese teaching, source selection,
map-first framing, the intended zone of proximal development, and the actual
next track unit depend on ambient context rather than the model entrypoint.

This is broader than a missing Chinese instruction. The complete
mission-to-lesson data flow is underbound.

### F-2. Demonstrated capability has two candidate authorities

Generated map mastery is derived from linked learning records, while normalized
session capability is derived from append-only YAML evidence. The v1.1 plan
intentionally keeps legacy record mastery visible, so differing values are not
by themselves a calculation contradiction.

The architectural defect is ownership ambiguity. A learner, model, and site can
still receive two answers about prior capability without a contract explaining
whether session events are raw observations, whether records are reviewed
capability summaries, and which projection selects the next lesson.

For example, `partial-failure` is `not started` in a generated track map and
`usable` in session-derived state. An existing reusable lesson for `program`,
`process`, or `service` is not mastery evidence and therefore does not create a
contradiction; it does show that lesson inventory and capability are different
objects.

### F-3. Review cues can dominate curriculum selection without owning it

The tutor order begins with "a due, important prior concept." The word
`important` gives the tutor discretion, so the three items due on 2026-08-28 do
not mechanically outrank every resume point and do not prove inevitable
starvation.

The remaining risk is real: importance is not defined from the mission,
curriculum, prerequisite structure, or learner record. Repeated next-day
`partial` results can repeatedly surface the same small concept set and crowd
out the resumed Web unit, depending on model judgment.

The scheduler should own review-cue projection only. It should not own track
progression or require every lesson target to be a canonical concept node.

### F-4. Resume supports prose checkpoints but lacks a structured lesson unit

The v1 schema requires `resume.from` and `resume.next` to be known concept IDs.
The free-text `resume.summary` can and does record "continue the Web lesson"
with a precise prose checkpoint. It is therefore incorrect to say the schema
has no way to record that intention.

It has no structured lesson identifier, unit kind, curriculum position, or
machine-checkable checkpoint. The latest resume points structurally to
`program` while its summary describes a connected document/browser/server
lesson. A client can display the prose but cannot reliably resolve or validate
the intended lesson artifact.

### F-5. Graph sparsity limits navigation coverage, not teachability

Only seven established computing concepts are canonical graph nodes, so graph
views and concept due projection cover a small part of both tracks. The
Bioinformatics Systems map cannot expose E-value, orthology, evidence identity,
or most curriculum depth as canonical nodes.

That does not mean the lesson loop must wait for graph growth. A bounded lesson
may teach a connected capability using a curriculum entry, lesson artifact,
trusted source, or demonstrated prerequisite without promoting every term into
`concepts/`. Coupling schedulability to canonical promotion would create
pressure to weaken the terminology gate.

Incremental evidence-backed concept promotion remains appropriate for graph
quality, but it is not the prerequisite for advancing the curriculum.

### F-6. Assisted success leaks into capability and review intervals

`scripts/build-learning-state.py` promotes a passing transfer to `usable`
without requiring `assisted: false`. The success count used for 1/7/21/60-day
review intervals also counts assisted passes. `retained` correctly filters its
later transfer candidate, but earlier passing evidence and the lower capability
states do not consistently apply that boundary.

The 2026-08-27 assisted `partial-failure` pass is not proof that this event first
created `usable`: an earlier unassisted transfer pass already existed. It does
show that an assisted pass can extend the success interval. A minimal synthetic
case with only one assisted transfer is required to prove first-promotion
behavior directly.

Event IDs are validated for timestamp and stable syntax but are not coupled to
evidence. Resume-only `*-exposure` files therefore expose a schema semantics
gap, not fabricated evidence: `evidence: []` remains authoritative about the
absence of an observed check.

### F-7. The workspace is a repository-specific extension of Teach

The workspace is correctly marked `kind: personal-learning`, but its durable
formats extend the generic Teach layout: records are track-nested and use mixed
number/date naming, most reusable lessons are semantic-name Markdown files, and
the workspace adds concepts, histories, session YAML, generated maps, and a
site.

Those extensions are not inherently defects. They mean the repo-local
`learning-lab-tutor` is an adapter with its own compatibility contract, not a
drop-in copy of generic Teach. The repository should preserve established paths
rather than bulk-renaming artifacts, while documenting which Teach outcomes it
implements and where it deliberately differs.

### F-8. The local terminology gate is stricter than generic Teach

Generic Teach permits a personal glossary to compress workspace language after
the learner demonstrates it. Repository `AGENTS.md` instead requires every
`GLOSSARY.md` and `concepts/` label to be an exact modern professional term
corroborated by two independent authoritative sources.

Under the repository-local rule, established terms such as E-value, ortholog,
and paralog have supporting sources in the Bioinformatics Systems resource
index. Repository-local phrases such as sequence-level reuse, exact evidence
reuse, and reusable terminal evidence do not currently establish exact-label
professional adoption. They belong in lesson or record prose unless the audit
finds the required independent evidence.

This is a repository-policy compliance finding, not a universal claim that
personal compressed language is pedagogically invalid. The complete glossary,
not only these examples, still requires an exact-label audit.

### F-9. Historical grounding can expand beyond the selected lesson win

The historical evidence gate correctly prevents invented motive, lineage, and
priority. The tutor skill currently requires an adequate historical frame
whenever a matching dossier exists. Teach instead asks for only the knowledge
required for one tangible lesson win.

History should remain mandatory for historical claims but conditional as a
teaching increment: include the dossier when it materially supports the selected
win, and otherwise preserve the bounded lesson without manufacturing or forcing
history.

### F-10. Model reliability has not been evaluated

The state validator, skill-text tests, and stored session YAML prove structural
capability. They do not prove that a model reads the intended sources, teaches
in Chinese, waits for retrieval, avoids revealing a due answer, grades evidence
truthfully, or advances a curriculum coherently.

The supported conclusion is that reliable pedagogical execution is not yet
established. A stronger claim requires representative cases with fixed model,
context, tools, fixtures, and scoring; repeated runs are needed when model
variance can change the decision.

## Corrected Architecture Direction

The next design should use this authority flow:

```text
MISSION + NOTES + trusted RESOURCES + demonstrated learning records
                              |
                              v
             one bounded, mission-linked lesson win
                              |
                              v
           curriculum / map / history / case evidence
                              |
                              v
                 observed session evidence + resume
                      |                   |
                      v                   v
       reviewed capability record    review-cue projection
```

The key decisions are:

- learning records own reviewed demonstrated capability;
- session events own raw observations, durable resume, and review-cue inputs;
- the scheduler projects review cues but does not own curriculum progression;
- the knowledge graph owns professional concept navigation and relationships,
  not the set of teachable lesson units;
- the tutor must read the learner contract before selecting a lesson;
- generated views label capability and review cues by their distinct owners.

The executable follow-up is the
[v1.4 mission-led learning loop implementation plan](../implementation-plans/20260827-v1.4-mission-led-learning-loop-implementation-plan.md).

## What Must Not Be Reopened By This Review

- Inferring durable capability solely from a `*-mastered.md` filename.
- Automatically promoting glossary or curriculum phrases into `concepts/` to
  make them schedulable.
- Treating a due cue as mandatory curriculum ownership.
- Manufacturing history where the required source support is absent.
- Rewriting append-only v1 session events to make a new schema look uniform.
- Bulk-renaming established track records or lessons merely to resemble generic
  Teach defaults.
- Claiming model reliability from static validation alone.
